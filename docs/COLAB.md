# Colab operating guide

The notebook `notebooks/runner.ipynb` is a thin wrapper:

- Every step runs `tools/<tool>.py --config <name>` from this repository.
- Each tool runs in a fresh subprocess with `PYTHONPATH=src`.
- The notebook kernel never imports research code.
- The notebook is generated by `tools/build_notebook.py` and committed without outputs.

## First run (Phase 0, CPU only)

1. **Open the notebook** in Colab: *File → Open notebook → GitHub*, then `meteorboyF/Anomaly-memory-compression` → `notebooks/runner.ipynb`.
2. **Use a CPU runtime:** *Runtime → Change runtime type → CPU*. Do not attach a GPU.
3. **Run Cell 1 (setup).** It does the following, in order:
   - mounts Drive (authorise when asked);
   - clones the public repository into `/content/Anomaly-memory-compression`;
   - checks out `main`;
   - installs the CPU dependencies (skipped when the fingerprint is unchanged);
   - prints the git SHA, the hardware and the free local disk;
   - prints `status()`.

   Expected: `[refresh] already up to date at <sha>`, `deps[cpu]: installed=…`, `dataset archive marker: absent`.
4. **Run Cell 2 (dataset → Drive).** It downloads 5.26 GB to local disk (resumable), hashes it, safely extracts it, checks the 15 categories, every image–mask pair and the published per-category counts, then copies the archive atomically to Drive and writes `…/datasets/archives/mvtec_anomaly_detection.tar.xz.verified.json`.
   - The first run should take roughly 10–30 min; this has not been measured yet and depends on the server's speed.
   - Expected final banner: `DATASET READY. Archive on Drive (verified): …`.
   - Re-running prints `verified archive already on Drive … skipping download`.
5. **Run Cell 3 (CPU checks).**
   - `metric_selfcheck`: must print `metric self-check PASSED`.
   - `profile_data`: dataset hash, split hash, defect-area quantiles, erased-by-crop counts, duplicates.
   - `evaluator_sanity`: constant/random give ≈0.5 AUROC and ≈0.15 AU-PRO; oracle gives 1.0, minus any defects erased by the crop.
   - `evaluator_sanity_native`: the native-resolution protocol, the most memory-heavy step. If the CPU runtime runs out of RAM, report it; the fix is a code change, not a bigger runtime.
6. **Run Cell 11** (status + artifact verification), then *Runtime → Disconnect and delete runtime*.
7. **Send me** the outputs of Cells 2, 3 and 11. A copy of every log is also on Drive under `artifacts/logs/`.

## Manual dataset fallback

If Cell 2 prints **ACQUISITION FAILED** with manual instructions:

1. Open https://www.mvtec.com/research-teaching/datasets/mvtec-ad/downloads and click the entry for the **whole dataset** (≈4.9 GB). If MVTec shows a form first, fill it in yourself.
2. The file must be named `mvtec_anomaly_detection.tar.xz` and be 5,264,982,680 bytes.
3. Upload it to `MyDrive/Research/Anomaly-memory-compression/datasets/archives/` (create the folders if needed).
4. **Leave it compressed.** Do not extract it.
5. Re-run Cell 2. It detects the upload and verifies it: XZ magic, exact size, SHA-256, safe extraction, structure and counts. Only then does it write the marker.

## The repair loop (no kernel restart for ordinary fixes)

1. A cell fails. The driver raises with the exit code and its meaning:
   - **1** = tool error (send the traceback)
   - **3** = refused by a safeguard (gate, allocation, dirty checkout, active run); nothing computed
   - **4** = config error
2. I fix it on the laptop, run the tests, commit and push.
3. You run **Cell 4** (`refresh_code()`). It fast-forwards the checkout, prints the new SHA, reloads the driver, and flags dependency changes separately.
4. Re-run the failed cell. Results are never mixed:
   - If the fix touched a tool's scientific modules, the run gets a new experiment identity.
   - Otherwise a complete run is skipped and a partial run is resumable with `resume=True`.

When you **do** need *Runtime → Restart session* (then re-run Cell 1):

- a compiled dependency changed (torch, faiss, numpy, scipy);
- the environment is incompatible;
- the Drive mount died ("Transport endpoint is not connected").

A dead mount is treated as a dead runtime. Do not retry it in a loop: restart, re-run Cell 1 (and Cell 2 to re-stage data), then resume.

A lost runtime loses local disk, but Drive keeps the archive and every completed artifact. Cell 1 + Cell 2 restore the state idempotently.

## Accelerator cells (blocked until approval)

Cells 5–9 do nothing unless all three conditions hold:

1. you set `ENABLE_ACCELERATOR = True`;
2. `configs/control/gates.yaml` has the phase approved;
3. `configs/control/allocations.yaml` holds an approved allocation covering the config.

I change those files only after you approve in chat. The tools re-check (2) and (3) themselves, so **Run all is safe**.

For an approved batch:

1. Switch to the approved GPU: *Runtime → Change runtime type*.
2. Re-run Cells 1–2.
3. Set `ALLOCATION_ID` and `CU_BALANCE_NOW` in Cell 5, then run Cells 5 → 6 (smoke) → 7 → 8.
4. Run **Cell 11**. It verifies all artifacts, closes the session in the usage log, and prints the shutdown instruction.
5. Then **Runtime → Disconnect and delete runtime**. Stopping a Python subprocess does not release the GPU, and an idle attached GPU keeps billing. Never use keep-alive tricks.
